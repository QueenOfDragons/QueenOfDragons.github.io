Da SAS a Python: perché non basta "tradurre"

Molte aziende stanno spostando i loro programmi SAS su Python, spesso facendoli tradurre in automatico, anche con l'intelligenza artificiale. Il codice che esce è pulito, gira senza errori... e dà numeri diversi. Nessun avviso, nessun messaggio rosso: semplicemente, in fondo al report, i conti non tornano più.

Succede perché SAS fa tante cose "da solo", in silenzio, e chi traduce riga per riga non le vede. Qui sotto c'è un esempio. Il programma e i dati sono inventati, ma i comportamenti di SAS e di pandas (la libreria Python più usata per lavorare con le tabelle) sono quelli reali.

Il caso: ritardi di pagamento in una banca

Una banca ha tre tabelle: le rate dei prestiti (quanto e quando si deve pagare), i pagamenti effettivamente arrivati e una tabella di lookup con il segmento del cliente (RETAIL, SME, large corporate...). Una rata può essere pagata in più volte, oppure non essere pagata affatto. Per ogni rata vogliamo sapere quanto resta da pagare, il ritardo massimo accumulato dal prestito, i mesi di scaduto di ogni rata e da quanti mesi di fila il cliente non paga. Sono i mattoni su cui poi si costruiscono esposizione, default e PD (probabilità di default).

Passo 1: unire rate e pagamenti

SAS 
/* Data di riferimento: fine del mese precedente */
%let data_rif = %sysfunc(intnx(month, %sysfunc(today()), -1, E));
/* nell'esempio: 31OCT2026 */

data work.rate_pag (keep=id_prestito n_rata data_scadenza
                         data_pagamento importo_pagato residuo);
  merge dwh.rate      (in=in_rata
                       where=(data_scadenza  <= &data_rif))
        dwh.pagamenti (where=(data_pagamento <= &data_rif));
  by id_prestito n_rata;
  if in_rata;
  /* residuo progressivo sui pagamenti parziali */
  residuo = sum(residuo, -importo_pagato);
  format residuo commax12.2;
run;
Python, traduzione "a macchina" 
chiavi = ["id_prestito", "n_rata"]
df = rate.merge(pagamenti, how="left",
                on=chiavi)
df["importo_pagato"] = (
    df["importo_pagato"].fillna(0))
df["residuo"] = (df["residuo"]
                 - df["importo_pagato"])

Trappola 1: il MERGE uno-a-molti "ricorda"

Il residuo progressivo qui è voluto, ed è un modo elegante di ottenerlo in SAS. Nel MERGE con BY, quando una rata ha due pagamenti, SAS legge la riga della rata una volta sola: sulla seconda riga le variabili che vengono da RATE restano nel PDV (l'area di lavoro del passo DATA) con il valore già modificato alla riga prima. Così residuo scala da solo: 500 − 200 = 300, poi 300 − 300 = 0.

Chi traduce vede solo una sottrazione. Il merge di pandas copia il valore originale su ogni riga: 500 − 200 = 300, poi 500 − 300 = 200. La rata risulta ancora insoluta anche se è stata pagata tutta.

Python, versione fedele a SAS 
pagamenti = pagamenti.sort_values(chiavi, kind="stable")   # stesso ordine del BY di SAS
df = rate.merge(pagamenti, how="left", on=chiavi)
df["importo_pagato"] = df["importo_pagato"].fillna(0)
df["residuo"] = df["residuo"] - df.groupby(chiavi)["importo_pagato"].cumsum()

Passo 2: la storia di ogni prestito

SAS 
/* ciclo DO: un'iterazione del passo DATA per prestito */
data work.storia;
  if 0 then set dwh.segmenti(keep=id_prestito segmento);
  if _n_ = 1 then do;
    /* lookup del segmento cliente, caricato una volta */
    /* l'ultimo caricato vince */
    declare hash seg(dataset:'dwh.segmenti',
                     duplicate:'r');
    seg.defineKey('id_prestito');
    seg.defineData('segmento');
    seg.defineDone();
  end;
  do until (last.id_prestito);
    set work.rate_pag;
    by id_prestito n_rata;
    if first.id_prestito then do;
      /* find fallito: il valore NON si azzera */
      if seg.find() ne 0 then segmento = 'ND';
    end;
    if last.n_rata then do;
      giorni_rit  = intck('day', data_scadenza,
                          data_pagamento);
      rit_max     = max(rit_max, giorni_rit);
      mesi_rit    = intck('month', data_scadenza,
                    coalesce(data_pagamento, &data_rif));
      insoluta    = (residuo > 0.005);
      mesi_consec = ifn(insoluta, sum(mesi_consec, 1), 0);
      output;
    end;
  end;
  label rit_max     = 'Ritardo massimo (giorni)'
        mesi_rit    = 'Mesi di scaduto'
        mesi_consec = 'Mesi consecutivi di insoluto';
run;
Python, traduzione "a macchina" 
st = df.drop_duplicates(chiavi,
                        keep="last").copy()
st = st.merge(segmenti, how="left",
              on="id_prestito")
g = st["id_prestito"]
st["giorni_rit"] = (st["data_pagamento"]
                    - st["data_scadenza"]).dt.days
st["rit_max"] = (st.groupby(g)["giorni_rit"]
                 .cummax())
fine = st["data_pagamento"].fillna(data_rif)
st["mesi_rit"] = ((fine - st["data_scadenza"])
                  .dt.days // 30)
ins = st["residuo"] > 0.005
blocco = (~ins).groupby(g).cumsum()
st["mesi_consec"] = (ins.astype(int)
                     .groupby([g, blocco])
                     .cumsum())

Trappola 2: il ciclo DO e i valori mancanti

Nel ciclo DO il passo DATA gira una volta per prestito: le variabili calcolate tornano a missing all'inizio di ogni prestito senza bisogno di RETAIN né di FIRST., e dentro il ciclo si accumulano. La funzione MAX poi ignora i missing: per una rata non pagata il ritardo massimo resta quello di prima.

Il cummax di pandas invece lascia NaN (il valore mancante di Python) proprio su quella riga, e se è l'ultima del prestito il ritardo massimo sparisce dal report. Con il max() di Python riga per riga va anche peggio: max(nan, -1) restituisce nan, max(-1, nan) restituisce -1. Il risultato dipende dall'ordine degli argomenti.

Trappola 3: INTCK non conta i giorni

intck('month', ...) conta quante volte si passa un confine di mese, non quanti mesi "pieni" sono trascorsi: dal 31 agosto al 25 settembre fa 1. È esattamente la logica delle fasce di scaduto per mese di competenza.

La traduzione più comune, giorni diviso 30, dà 0. E con un pagamento in anticipo di un giorno va peggio: in Python -1 // 30 fa -1, perché la divisione intera arrotonda verso il basso, mentre SAS dà 0. Un mese di scaduto negativo, senza nessun errore.

Trappola 4: la tabella di lookup con chiavi doppie

L'oggetto hash carica SEGMENTI in memoria una volta sola e con duplicate:'r' tiene l'ultima riga per chiave: il prestito 1002 è SME. Attenzione anche al find(): se la chiave non c'è, il valore resta quello del prestito precedente, perché le variabili lette con SET non si azzerano. Per questo il ramo 'ND' non è un vezzo.

Il merge di pandas invece abbina il 1002 a tutte e due le righe: le sue rate raddoppiano, da 3 a 6, e con loro l'esposizione che verrà sommata dopo. Nessun errore, a meno di chiedere a pandas di controllare con validate.

Python, versione fedele a SAS (un pezzo) 
seg = segmenti.drop_duplicates("id_prestito", keep="last")        # duplicate:'r' dell'hash
st = st.merge(seg, how="left", on="id_prestito", validate="many_to_one")
st["segmento"] = st["segmento"].fillna("ND")
st["rit_max"] = (st.groupby(g)["giorni_rit"].cummax()
                 .groupby(g).ffill())                  # MAX di SAS: i mancanti non contano
st["mesi_rit"] = ((fine.dt.year  - st["data_scadenza"].dt.year) * 12
                  + (fine.dt.month - st["data_scadenza"].dt.month))   # INTCK 'month' conta i confini di mese
